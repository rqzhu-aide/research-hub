# Research Hub — UI Audit (2026-07-30)

Scope: visual/appearance improvements to highlight **user input & control**
and **feedback summaries**. Audited: `templates/` (13 files), `static/style.css`
(1291 lines), `static/app.js`, rendered against project-004.

The design system itself is strong: IBM Plex pairing, dual themes, consistent
status hues (teal/blue/amber/rose), one indigo accent, careful tokens. The
gaps are in *information hierarchy*, not styling fundamentals.

## Findings — user input & control

**U1. The user's voice is the least-visible element on the launch form.**
The instruction textarea (`_tab_phase.html:846-851`) is the single most
important user input — it steers the entire agent team and is frozen into the
run record — yet it sits near the bottom of a ~450-line form, styled as a
plain textarea with a small label. Everything around it (method picker,
status spans, selects) is visually louder.

**U2. No pre-launch summary of what the user is committing to.**
The form freezes method identity, context sources, mode, and rounds at launch
(`field-help` at `:691-699` explains this in prose), but there is no
digestible "you are about to launch X" summary. The only feedback is the
launch-hint spans (`:893-907`) which mostly report *blockers*, never an
affirmative plan. For a system whose philosophy is "user is in control", the
control act (launch) lacks a confirmation of *what* is being controlled.

**U3. Launch confirmation is a native browser confirm.**
`data-confirm="Launch this run now?"` (`:442`). For a consequential action
that starts a multi-agent run and freezes state, a native dialog is the
weakest possible confirmation surface — no recap, no emphasis on what will
be frozen.

**U4. Branch record statuses are dense and unscannable.**
Each method option renders 4 verbose `record-status` spans with reasons
(`:580-611`), ~15 words each, in 0.68rem type. Scanning 3 methods × 4 phases
is a wall of small colored text. The legend (`:519-524`) helps, but the
per-method state could be a compact 4-segment rail (P2·P3·P4·P5) with detail
on demand — the detail panel on the right already exists (`:632-689`).

## Findings — feedback summaries

**F1. Decision records are structured, but the UI shows only plain text.**
Runs capture rich decision data — `main_evidence`, `principal_risk`,
`smallest_decision_changer`, `option_consequences` (proceed/rerun/defer…),
`rerun_question`, `scientific_record_changes`. The UI surfaces only
`summary_highlight` (computed text, `web_phase_data.py:277`, rendered at
`_tab_phase.html:375-393`). The "what should I decide next" content the
agents explicitly produce never reaches the user. This is the single largest
feedback gap.

**F2. No "what changed since last time" framing on completed runs.**
The run header shows status badges + outcome, and `run-record-comparison`
(`:358-371`) appears only when record/attempt diverge. A completed rerun
doesn't visually answer "what's different now?" — the `rerun_comparison`
field exists in decision records for exactly this.

**F3. Strengths to preserve.** The active-run card (`_run_progress.html`) is
well done: stage list, elapsed time, "Your direction" echo (`:118-123`),
context-change warning, cancel/cleanup recovery flows. Overview phase cards
and timeline are good. Keep all of it.

## Proposals (prototype: `phase-tab-redesign-prototype.html`)

| # | Proposal | Addresses | Effort |
|---|---|---|---|
| P1 | **Run plan digest** — a live card above the launch button summarizing method, mode, rounds, context policy, and frozen inputs; updates as the user changes selections | U2 | JS + template (moderate) |
| P2 | **Elevated direction panel** — restyle the instruction box as the form's hero input: accent-tinted surface, "Your direction — frozen into the run record" framing, char count | U1 | CSS + template (small) |
| P3 | **Decision brief card** — structured summary in the upper panel: outcome, what changed (`rerun_comparison`), main evidence, principal risk, next options (`option_consequences` as actionable rows) | F1, F2 | backend context + template (moderate) |
| P4 | **Branch status rail** — replace the 4 verbose spans per method with a compact P2–P5 dot rail; reasons stay in the detail panel | U4 | template + CSS (small) |
| P5 | **Inline launch review** — replace the native confirm with an inline review step that shows the plan digest and requires an explicit confirm click | U3 | JS (small, once P1 exists) |

P1 and P3 are the high-impact pair: they close the loop "I tell the system
what to do → the system tells me what it decided and what my options are".
